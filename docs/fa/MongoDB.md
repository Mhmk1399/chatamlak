# MongoDB

گفتگوی اوج برای پایگاه دادهٔ فعال از درایور بومی Node.js نسخهٔ ۷ و replica set در MongoDB 8 استفاده می‌کند. SQLite و PostgreSQL فقط منبع ورود دادهٔ قدیمی هستند و موتور جایگزین اجرای برنامه نیستند. یک `mongod` مستقل بدون replica set کافی نیست؛ چون تغییر پیام و ثبت رویداد مربوط به آن از تراکنش استفاده می‌کند.

## چه داده‌ای در MongoDB ذخیره می‌شود

حساب‌ها، عضویت‌ها، نشست‌ها، گفتگوها، پیام‌ها، واکنش‌ها، نظرسنجی‌ها، زمان‌بندی‌ها، تنظیمات، متادیتای فایل و رویدادها در collectionهای ایندکس‌شده ذخیره می‌شوند. هر پیام سند جداگانه است و به آرایه‌ای با رشد نامحدود داخل گفتگو اضافه نمی‌شود. UUIDهای عمومی و نام فیلدهای API حفظ می‌شوند و متن پیام‌ها قالب رمزگذاری فعلی برنامه را نگه می‌دارد.

**متادیتای** پیوست و آواتار در MongoDB است. محتوای باینری فایل‌ها همچنان از provider محلی یا سازگار با S3 استفاده می‌کند و این تغییر آن‌ها را به GridFS منتقل نمی‌کند. از volume آپلود محلی یا اشیای راه‌دور، جدا از دیتابیس نسخهٔ پشتیبان بگیرید و کلیدهای لازم برای رمزگشایی را حفظ کنید.

## چرخهٔ داده‌های فنی

لغو یک نشست، برچسب متناظر آن در `session_devices` و خود نشست را در یک تراکنش حذف می‌کند. لغو همهٔ نشست‌های کاربر، از جمله هنگام حذف حساب، توکن نشست‌ها را با cursor می‌خواند و برچسب‌های متناظر را در دسته‌های حداکثر **۱۰۰تایی** داخل تراکنش حذف می‌کند. برچسب دستگاه‌های حساب‌های دیگر حفظ می‌شود.

لغو زمان‌بندی مجاز با `cancelSchedule`، متن تکراری `body` و `lease_until` را `null` می‌کند. پایان موفق با وضعیت `sent` در `finishSchedule` هم همین رفتار را دارد؛ پیام منتشرشده از رکورد معمول پیام گفتگو استفاده می‌کند. زمان‌بندی‌های در انتظار و ناموفق، متن را برای اصلاح یا تلاش مجدد نگه می‌دارند. رکورد زمان‌بندی و API موجود حفظ می‌شوند.

این عملیات هنگام لغو نشست یا رسیدن زمان‌بندی به وضعیت پایانی، از انباشته‌شدن دادهٔ فنی زائد جلوگیری می‌کنند؛ پاک‌سازی سراسری دادهٔ قبلی یا حذف collection انجام نمی‌دهند. API یا collection جدیدی معرفی نشده است.

## پیش‌نیازها

- Node.js نسخهٔ `>=24.18.0` و npm نسخهٔ `>=11.18.0`.
- MongoDB 8 با replica set یا استقرار مناسب Atlas.
- primary در دسترس، پشتیبانی تراکنش و کاربر دیتابیسی با اجازهٔ خواندن و نوشتن collectionهای برنامه و ایجاد ایندکس‌های آن‌ها.
- FFmpeg برای پردازش محلی رسانه؛ [ورکر مدیا](./Media-Worker) را ببینید.

replica set تک‌عضوی برای توسعه و پشتیبانی تراکنش مفید است، اما افزونگی چندعضوی ندارد. برای تطبیق نمونه‌ها با محیط خود از [راهنمای رسمی replica set توسعه](https://www.mongodb.com/docs/manual/tutorial/deploy-replica-set-for-testing/) استفاده کنید.

## تنظیم محیط

با ویرایشگر یا دستور پوسته، `.env.example` را به `.env` در ریشهٔ مخزن کپی کنید. URI در فایل نمونه عمداً خالی است:

```dotenv
DB_CLIENT=mongodb
MONGODB_URI=
MONGODB_DATABASE=ouj_chat
```

رشتهٔ اتصال در دسترس خود را در **`.env`** وارد کنید، نه در کد ثبت‌شدهٔ مخزن. برای replica set محلی این راهنما:

```dotenv
DB_CLIENT=mongodb
MONGODB_URI=mongodb://localhost:27017/ouj_chat?replicaSet=ouj-rs
MONGODB_DATABASE=ouj_chat
```

مقدار `DB_CLIENT=mongodb` را نگه دارید یا انتخاب‌گر قدیمی SQL را حذف کنید تا پیش‌فرض فعلی اعمال شود؛ مقدارهایی مانند `postgres` یا `sqlite3` در این شاخه رد می‌شوند. URI خالی به معنی انتخاب مخفی یک دیتابیس محلی یا بازگشت به SQLite نیست. پیش از اجرای سرور آن را تنظیم کنید. نام دیتابیس انتخاب‌شده در نمونه‌های مختلف برنامه یکسان باشد. برای جزئیات اتصال replica set، [راهنمای مقصد اتصال MongoDB](https://www.mongodb.com/docs/drivers/node/current/connect/connection-targets/) را ببینید.

## MongoDB محلی با Docker

برای توسعه با اجرای برنامه روی میزبان، از ریشهٔ مخزن فایل Compose مخصوص آن را اجرا کنید:

```sh
docker compose -f docker-compose.mongo.yaml up -d
```

این فایل replica set تک‌عضوی MongoDB 8 با نام `ouj-rs` اجرا می‌کند، فقط `127.0.0.1:27017` را منتشر و `localhost:27017` را اعلام می‌کند. تا آماده‌شدن primary صبر کنید. نمونهٔ محلی بدون اطلاعات محرمانهٔ زیر را در `.env` خصوصی قرار دهید؛ سپس برنامه را با `npm run dev` روی میزبان اجرا کنید:

```dotenv
MONGODB_URI=mongodb://127.0.0.1:27017/ouj_chat?replicaSet=ouj-rs
MONGODB_DATABASE=ouj_chat
```

این فایل توسعه از فایل اصلی Compose برنامه جداست. آن‌ها را ترکیب نکنید؛ کانتینر برنامه نمی‌تواند با `localhost` اعلام‌شدهٔ دیتابیس به کانتینر دیگری برسد. مجموعهٔ اصلی برنامه به replica set در دسترس خارجی یا URI مربوط به Atlas نیاز دارد. `MONGODB_URI` در فایل ثبت‌شدهٔ `.env.example` همچنان خالی می‌ماند.

راه دیگر، مقداردهی دستی replica set توسعه است. اگر دیتابیس Compose در حال استفاده از پورت `27017` است، کانتینر دوم زیر را روی همان پورت اجرا نکنید:

در این نمونه، MongoDB داخل کانتینر و Node.js روی میزبان اجرا می‌شوند:

```sh
docker run -d --name ouj-mongo -p 127.0.0.1:27017:27017 -v ouj-mongo-data:/data/db mongo:8 --replSet ouj-rs --bind_ip_all
docker exec -it ouj-mongo mongosh
```

در پوستهٔ تعاملی MongoDB، مجموعهٔ جدید را فقط یک بار مقداردهی کنید:

```javascript
rs.initiate({ _id: "ouj-rs", members: [{ _id: 0, host: "localhost:27017" }] })
rs.status()
```

تا رسیدن عضو به وضعیت `PRIMARY` صبر کنید؛ سپس از `mongosh` خارج شوید و URI محلی بالا را تنظیم کنید. volume نام‌دار، فایل‌های دیتابیس را پس از راه‌اندازی دوبارهٔ کانتینر نگه می‌دارد. این نمونهٔ بدون احراز هویت و محدود به loopback برای توسعهٔ محلی است؛ محیط تولید به استقرار احرازهویت‌شده و شبکهٔ محدودشدهٔ مناسب نیاز دارد.

اگر برنامه هم داخل Docker اجرا می‌شود، `localhost` به خود کانتینر برنامه اشاره می‌کند. از نام میزبان شبکهٔ سرویس دیتابیس و تنظیم replica set با نام‌های اعلام‌شده‌ای استفاده کنید که از همهٔ کلاینت‌ها قابل دسترسی باشند. [نصب Docker](./Installation-Docker) و [راهنمای رسمی Docker](https://www.mongodb.com/docs/manual/administration/install-community-docker/) را ببینید.

## MongoDB محلی بدون Docker

MongoDB 8 و `mongosh` را مطابق [دستورالعمل نصب سیستم‌عامل](https://www.mongodb.com/docs/manual/installation/) نصب کنید. یک پوشهٔ دادهٔ خالی بسازید و عضو محلی را اجرا کنید:

```sh
mongod --dbpath ./mongo-data --replSet ouj-rs --bind_ip localhost --port 27017
```

در ترمینال دیگر `mongosh` را اجرا کنید و همان دستورهای `rs.initiate(...)` و `rs.status()` بالا را بزنید. هنگام استفاده از برنامه، ترمینال یا سرویس `mongod` باید در حال اجرا بماند.

## MongoDB Atlas

1. استقراری سازگار با نسخهٔ MongoDB موردنیاز بسازید یا انتخاب کنید.
2. برای برنامه **کاربر دیتابیس** بسازید؛ حساب ورود به داشبورد Atlas حساب جداگانه‌ای است.
3. آدرس سرور برنامه را به فهرست مجاز دسترسی شبکهٔ Atlas اضافه کنید.
4. از **Connect → Drivers → Node.js** رشتهٔ اتصال را کپی و در `MONGODB_URI` فایل خصوصی `.env` یا تنظیمات محرمانهٔ استقرار وارد کنید. جایگزین‌های نام کاربری و رمز را تکمیل کنید و TLS را فعال نگه دارید.
5. مقدار `MONGODB_DATABASE=ouj_chat` را تنظیم کنید و فقط پس از آماده‌شدن اتصال، برنامه را اجرا کنید.

برای مسیر فعلی داشبورد و پیش‌نیازهای دسترسی، [راهنمای اتصال درایور در Atlas](https://www.mongodb.com/docs/atlas/driver-connection/) را ببینید. اطلاعات ورود را در مستندات، آرگومان دستور، تصویر یا فایل ثبت‌شدهٔ مخزن قرار ندهید.

## نصب و اجرای برنامه

پس از تنظیم URI، از ریشهٔ مخزن اجرا کنید:

```sh
npm install
npm --prefix client install
npm --prefix server install
npm --prefix worker install
npm run dev
```

برای ساخت فرانت‌اند تولید و اجرای API:

```sh
npm run build
npm start
```

MongoDB باید در دسترس بماند. ورکر و فضای ذخیره‌سازی را طبق راهنماهای خودشان تنظیم کنید؛ راه‌اندازی دیتابیس جایگزین تنظیم فایل‌ها یا FFmpeg نیست.

## ورود داده از نصب SQL قدیمی

ابتدا برنامهٔ قدیمی را متوقف کنید و از دیتابیس، فایل‌ها و کلیدهای رمزگذاری نسخهٔ پشتیبان بگیرید. MongoDB مقصد باید جدید و خالی باشد. ابتدا گزارش اجرای آزمایشی را بررسی کنید:

```sh
npm --prefix server run db:import-sql -- --source ./backups/ouj-chat.db --dry-run
npm --prefix server run db:import-sql -- --source ./backups/ouj-chat.db --apply
```

برای PostgreSQL، رشتهٔ اتصال قدیمی را در متغیر محیطی خصوصی `LEGACY_POSTGRES_URI` قرار دهید؛ URI دارای رمز را به‌عنوان آرگومان وارد نکنید:

```sh
npm --prefix server run db:import-sql -- --postgres --dry-run
npm --prefix server run db:import-sql -- --postgres --apply
```

گزارش ورود را بررسی کنید و سپس `npm --prefix server run db:check` را اجرا کنید. ابزار، منبع قدیمی را می‌خواند و در دیتابیس خالی انتخاب‌شدهٔ MongoDB می‌نویسد؛ فایل‌های آپلودشده را کپی نمی‌کند و به‌تنهایی موفقیت انتقال محیط تولید را ثابت نمی‌کند. پشتیبان منبع را تا بررسی حساب‌ها، عضویت‌ها، تعداد پیام‌ها، پیوند فایل‌ها، محتوای رمزگذاری‌شده و بازیابی رویدادها در استقرار خود نگه دارید.

## پشتیبان‌گیری و بازیابی

آرشیو برنامه Extended JSON فشرده‌شده با gzip (`.json.gz`) و شامل رکوردهای دیتابیس و اطلاعات کلیدهای رمزگذاری است:

```sh
npm --prefix server run db:backup -- --file ./backups/ouj.backup.json.gz
```

آرشیو را خصوصی نگه دارید. volume آپلود محلی یا پشتیبان اشیای راه‌دور و تنظیمات محیط لازم را هم حفظ کنید. آرشیو دیتابیس به‌تنهایی پشتیبان کامل فایل‌های باینری نیست.

برای بازیابی، تمام فرایندهای برنامه و ورکرهایی را که می‌توانند این دیتابیس را تغییر دهند متوقف کنید و سپس CLI آفلاین را اجرا کنید:

```sh
npm --prefix server run db:restore -- --file ./backups/ouj.backup.json.gz --yes --offline
npm --prefix server run db:check
```

گزینه‌های `--yes --offline` تأیید صریح بازیابی آفلاین هستند و خودشان سرویس‌های در حال اجرا را متوقف نمی‌کنند. بازیابی آنلاین از پنل مدیریت با HTTP `409` رد می‌شود تا اتصال‌های فعال به‌طور پنهانی جایگزین نشوند. snapshot ارائه‌دهنده یا `mongodump` و `mongorestore` گزینه‌های عملیاتی دیگری هستند؛ آرشیو BSON آن‌ها با قالب `.json.gz` برنامه یکسان نیست.

## آزمون‌ها

```sh
npm --prefix client run test:unit
npm --prefix server run test
npm --prefix server run test:mongo
```

اگر `MONGODB_TEST_URI` تنظیم نشده باشد، مجموعهٔ integration از replica set موقت و واقعی با `mongodb-memory-server` استفاده می‌کند. اجرای اول ممکن است به دریافت فایل اجرایی MongoDB نیاز داشته باشد. اگر دریافت خودکار در دسترس نیست، `MONGOMS_SYSTEM_BINARY` را به فایل اجرایی سازگار و نصب‌شدهٔ `mongod` اشاره دهید.

برای استفاده از replica set آزمایشی موجود، `MONGODB_TEST_URI` را به‌صورت خصوصی روی URI شامل **نام صریح دیتابیس اختصاصی آزمون** مانند `ouj_chat_test` یا `ouj_chat_e2e` تنظیم کنید. نام باید `test` یا `e2e` داشته باشد؛ دادهٔ آزمون ممکن است پاک شود. آن را به `ouj_chat` یا دیتابیس زندهٔ دیگری وصل نکنید. یک URI محلی و بدون اطلاعات محرمانه: `mongodb://localhost:27017/ouj_chat_test?replicaSet=ouj-rs`.

این دستورها شیوهٔ اجرای بررسی‌ها را توضیح می‌دهند؛ وجودشان ادعای انجام ورود داده، بازیابی، آزمون Atlas یا تست بار محیط تولید نیست.

فایل `server/test/mongo/dataLifecycle.test.js` حذف تراکنشی برچسب نشست، rollback، جداسازی حساب‌ها، دسته‌های محدود و حفظ متن زمان‌بندی را بررسی می‌کند. آن را فقط با پیکربندی آزمون واقعی MongoDB و دیتابیس اختصاصی توضیح‌داده‌شدهٔ بالا اجرا کنید.

## عیب‌یابی

| نشانه | بررسی |
|---|---|
| نبودن URI اتصال | `MONGODB_URI` را در تنظیم خصوصی تکمیل کنید؛ فایل نمونه عمداً خالی می‌ماند. |
| نیاز تراکنش به replica set | مجموعه را مقداردهی کنید و منتظر primary قابل‌نوشتن بمانید؛ سرور مستقل کافی نیست. |
| پایان مهلت انتخاب سرور | DNS، پورت‌ها، مجوزها، دسترسی شبکهٔ Atlas و دسترسی به تمام نام‌های اعلام‌شدهٔ replica set را بررسی کنید. |
| اتصال‌نداشتن کانتینر برنامه به localhost | نام سرویس در دسترس دیتابیس را به‌جای loopback کانتینر برنامه استفاده کنید. |
| رمزگشایی‌نشدن پیام یا فایل بازیابی‌شده | کلیدهای رمزگذاری و فایل‌های باینری متناظر را همراه با رکوردهای دیتابیس بازیابی کنید. |
| شکست دریافت فایل اجرایی آزمون MongoDB | فایل اجرایی محلی سازگار را با `MONGOMS_SYSTEM_BINARY` معرفی کنید یا replica set اختصاصی را با `MONGODB_TEST_URI` تنظیم کنید. |

برای عملیات مرتبط، [دستورهای دیتابیس](./Database-Commands)، [متغیرهای محیطی](./Environment-Variables) و [عیب‌یابی](./Troubleshooting) را ببینید.
