# به‌روزرسانی

این شاخه از MongoDB استفاده می‌کند، نه موتور قبلی SQLite یا PostgreSQL. به‌روزرسانی فایل‌های برنامه به‌تنهایی دادهٔ SQL را وارد نمی‌کند و replica set نمی‌سازد. پیش از اولین انتقال، [راهنمای MongoDB](./MongoDB) را بخوانید.

## پیش از ارتقا

نسخهٔ برنامه و تنظیم دیتابیس و فضای فایل را ثبت کنید. از رکوردها پشتیبان بگیرید و اطلاعات کلید رمزگذاری و volume آپلود یا اشیای S3 را جداگانه حفظ کنید:

```sh
npm --prefix server run db:backup -- --file ./backups/ouj.before-update.json.gz
```

نام آرشیو جدید انتخاب کنید؛ دستور بومی فایل موجود را پنهانی بازنویسی نمی‌کند. آرشیو اطلاعات کلید خصوصی دارد و باید محافظت شود. برای نقطهٔ بازیابی هماهنگ دیتابیس و فایل، نویسندگان را متوقف یا روش مستند provider را استفاده کنید.

## اولین انتقال از SQL

1. برنامهٔ قدیمی را متوقف و دیتابیس SQL، فایل‌ها و کلیدهای رمزگذاری آن را حفظ کنید.
2. replica set یا Atlas مناسب و دیتابیس مقصد جدید و خالی تنظیم کنید.
3. مقدار خصوصی `MONGODB_URI` را وارد و `DB_CLIENT=mongodb` و `MONGODB_DATABASE=ouj_chat` را نگه دارید.
4. dry run مناسب را اجرا و بررسی کنید؛ سپس صریحاً اعمال و `db:check` را اجرا کنید.
5. پیش از هدایت ترافیک، حساب‌ها، عضویت‌ها، شناسه‌های عمومی، پیام‌ها، رسانه و محتوای رمزگذاری‌شده را بررسی کنید.

دستور SQLite و PostgreSQL در [ورود دادهٔ قدیمی](./MongoDB#ورود-داده-از-نصب-sql-قدیمی) آمده است. این روند ادعای انجام موفق ورود داده نیست. ورود متادیتای دیتابیس، فایل آپلودها را کپی نمی‌کند.

## به‌روزرسانی نصب MongoDB موجود

پس از توقف نویسندگان و به‌روزرسانی سورس یا تصویر استقرار با روند معمول خود، از ریشهٔ مخزن وابستگی‌ها را نصب و دوباره بسازید:

```sh
npm install
npm --prefix client install
npm --prefix server install
npm --prefix worker install
npm run build
npm --prefix server run db:migrate
npm --prefix server run db:check
```

`db:migrate`، collectionها و ایندکس‌های MongoDB را آماده و بررسی می‌کند و مایگریشن SQL قدیمی را اجرا نمی‌کند. با `npm start` یا راه‌اندازی سرویس systemd یا کانتینر تنظیم‌شده، برنامه را اجرا کنید؛ سپس `/api/health`، ورود، رویداد زنده و رسانه را بررسی کنید. MongoDB و provider فایل هنگام بازیابی در دسترس بمانند.

## استقرار Docker و ابری

از تصویر ساخته‌شده با نسخهٔ سازگار MongoDB استفاده کنید و URI را در محیط خصوصی بدهید. تصویر تاریخی یا template زیرساختی که PostgreSQL می‌سازد، خودکار با مسیر دیتابیس جدید سازگار نیست.

ماندگاری MongoDB را از volume آپلود جدا نگه دارید. برای ورکر خارجی، تنظیم متناظر فایل، رمزگذاری و webhook را حفظ کنید. [Docker](./Installation-Docker) و [استقرار ابری](./Cloud-Deployment) را ببینید.

## بازیابی و بازگشت نسخه

پیش از بازیابی آرشیو MongoDB تمام نویسندگان را متوقف کنید:

```sh
npm --prefix server run db:restore -- --file ./backups/ouj.before-update.json.gz --yes --offline
npm --prefix server run db:check
```

بازیابی آنلاین پنل مدیریت، HTTP `409` برمی‌گرداند؛ از دستور نگه‌داری آفلاین استفاده کنید. اگر فایل باینری و تنظیم رمزگذاری هم تغییر کرده، نسخهٔ متناظر آن‌ها را بازیابی کنید.

نسخهٔ قدیمی SQL با صرف انتخاب کد آن روی MongoDB اجرا نمی‌شود. بازگشت از این مرز، نسخهٔ قدیمی و پشتیبان اصلی SQL و فایل و کلید آن را لازم دارد؛ تبدیل خودکار MongoDB به SQL وجود ندارد. بدون مسیر سازگاری مستند، دیتابیس جدیدتر را با برنامهٔ قدیمی سازگار فرض نکنید.

## نسخهٔ اسکریپت نصب

منوهای قدیمی `songbird-deploy` شامل انتخاب SQL، پشتیبان SQL و مایگریشن SQL بودند. تا وقتی نسخهٔ دقیق اسکریپت برای MongoDB به‌روز نشده، آن‌ها را روند قدیمی در نظر بگیرید. از دستورهای بومی [دستورهای دیتابیس](./Database-Commands) و فایل استقرار بررسی‌شده استفاده کنید و ورود یا بازگشت خودکار داده را فرض نکنید.
