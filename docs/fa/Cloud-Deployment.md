# استقرار ابری

گفتگوی اوج از MongoDB برای رکوردهای برنامه و provider محلی یا سازگار با S3 برای باینری فایل‌ها استفاده می‌کند. دیتابیس، فایل، کلیدهای رمزگذاری، مسیریابی بلادرنگ و پردازش رسانه را جداگانه برنامه‌ریزی کنید. پیش از ساخت کانتینرها، [MongoDB](./MongoDB) را ببینید.

## نمای معماری

| بخش | ماندگاری / مسئولیت |
|---|---|
| سرور وب و API | React، API احرازهویت‌شده و اتصال‌های WebSocket/SSE. |
| MongoDB 8 replica set یا Atlas مناسب | collectionهای ایندکس‌شده، پیام رمزگذاری‌شده و ثبت تراکنشی رویداد. |
| volume ماندگار یا فضای سازگار با S3 | باینری پیوست و آواتار؛ متادیتا در MongoDB است. |
| ورکر مدیا | FFmpeg با درخواست HTTP و callback؛ بدون اتصال مستقیم دیتابیس. |
| Redis در صورت تنظیم | pub/sub مشترک، کش نشست و صف پس‌زمینه. |

MongoDB مستقل بدون replica set برای تراکنش‌ها کافی نیست. UUIDهای عمومی و فیلدهای API حفظ می‌شوند و انتخاب MongoDB به API متفاوت کلاینت نیاز ندارد.

## تنظیمات برنامه در PaaS

وابستگی‌های ریشه، کلاینت، سرور و ورکر را متناسب با محیط ساخت نصب کنید. دستورهای معمول ساخت و اجرای API:

```sh
npm run build
npm --prefix server run start
```

از Node.js نسخهٔ `>=24.18.0` و npm نسخهٔ `>=11.18.0` استفاده کنید. پورت و probe سلامت را برای پلتفرم تنظیم کنید؛ مسیر probe API، `/api/health` است. پیش از وجود primary قابل‌نوشتن و موفقیت راه‌اندازی برنامه، ترافیک را وارد نکنید.

در محیط خصوصی یا تنظیمات محرمانهٔ پلتفرم قرار دهید:

```dotenv
DB_CLIENT=mongodb
MONGODB_URI=
MONGODB_DATABASE=ouj_chat
```

خط خالی جای‌نگهدار عمدی است: URI واقعی Atlas یا replica set را در تنظیم استقرار وارد کنید. مقدار خالی قابل‌اجرا نیست و SQLite را انتخاب نمی‌کند. TLS، مجوز و دسترسی شبکهٔ provider را اعمال کنید؛ [Atlas](./MongoDB#mongodb-atlas) را ببینید.

## ماندگاری فایل‌ها

فایل‌سیستم PaaS می‌تواند موقت باشد. MongoDB رکوردها را حفظ می‌کند، نه فایل‌های روی دیسک موقت برنامه را.

برای یک نمونه با ذخیره‌سازی محلی، volume ماندگار وصل کنید، `DATA_DIR` را روی mount تنظیم کنید و از آن پشتیبان بگیرید. برای میزبان‌های جداگانهٔ برنامه و ورکر، S3 مشترک و در دسترس هر دو مناسب‌تر است:

```dotenv
STORAGE_DRIVER=remote
STORAGE_ENDPOINT=https://your-object-storage-endpoint
STORAGE_BUCKET=ouj-uploads
STORAGE_ACCESS_KEY_ID=
STORAGE_SECRET_ACCESS_KEY=
```

مجوزها را خصوصی تکمیل کنید. CORS، دسترسی فایل ورکر و webhook را مطابق [فضای ذخیره‌سازی](./Object-Storage) و [ورکر مدیا](./Media-Worker) تنظیم کنید. متادیتا در MongoDB است و باینری‌ها به GridFS منتقل نشده‌اند.

## Railway {#استقرار-خودکار-با-railway-زیرساخت-به-عنوان-کد-iac}

از فایل‌های استقرار فعلی مخزن شروع و URI در دسترس replica set یا Atlas را تنظیم کنید. نمودارهای قدیمی Railway و دستورهای ساخت PostgreSQL، نسخهٔ SQL قدیمی را توصیف می‌کنند و معماری فعال نیستند. template و متغیرهایش را بررسی کنید؛ این راهنما ورود یک‌کلیکی داده یا ساخت خودکار MongoDB را تأیید نمی‌کند.

API و ورکر مستقل اختیاری را با provider فایل مشترک و callback معتبر اجرا کنید. اطلاعات اتصال را در محیط محرمانهٔ برنامه نگه دارید، نه آرگومان پوسته یا فایل زیرساخت ثبت‌شده.

## Render

از تعریف فعلی Docker یا سورس با `MONGODB_URI` و `MONGODB_DATABASE` استفاده کنید. برنامه به MongoDB ماندگار و فایل بادوام نیاز دارد؛ blueprint تاریخی PostgreSQL، دیتابیس MongoDB فعال نیست.

اگر کانتینر ورکر محلی را مدیریت می‌کند، پورت آن با پورت API متفاوت باشد. برای ورکر خارجی، `WORKER_URL` و callback را تنظیم کنید. خواب پلتفرم و شروع سرد را برای پیام زمان‌بندی‌شده، تماس و بازتاب پیوسته در نظر بگیرید؛ [کانال ریموت](./Remote-Channel-Setup) را ببینید.

## کانتینرها و Kubernetes

همهٔ نمونه‌ها باید دیتابیس MongoDB و تنظیم رمزگذاری سازگار داشته باشند. فضای باینری فایل باید از همهٔ نمونه‌ها و ورکرها یکسان در دسترس باشد. نام سرویس MongoDB و نام‌های اعلام‌شدهٔ replica set از کانتینرها قابل دسترسی باشند؛ `localhost` داخل pod برنامه، pod دیتابیس نیست.

فایل اصلی `docker-compose.yaml` سورس محلی برنامه را می‌سازد و به URI خارجی MongoDB نیاز دارد. فایل جداگانهٔ `docker-compose.mongo.yaml` یک replica set تک‌عضوی محدود به loopback برای اجرای Node.js روی میزبان راه‌اندازی می‌کند. آدرس اعلام‌شدهٔ `localhost:27017` آن، مقصد دیتابیس برای کانتینر دیگر یا استقرار PaaS نیست. این دو معماری را جدا نگه دارید؛ [نصب Docker](./Installation-Docker) و [MongoDB محلی](./MongoDB#mongodb-محلی-با-docker) را ببینید.

برای بلادرنگ چندنمونه‌ای، به‌جای fallback داخل فرایند، Redis مشترک تنظیم کنید. sticky session جای دیتابیس، فایل و مسیریابی مشترک را نمی‌گیرد. تماس، حضور، بازیابی رویداد، زمان‌بندی و retry ورکر را روی معماری خود بررسی کنید؛ فعال‌شدن MongoDB به‌تنهایی ادعای ظرفیت یا دسترس‌پذیری بالا نیست.

## پشتیبان، انتقال و ارتقا

- پشتیبان MongoDB، فایل‌ها و تنظیم رمزگذاری را با هم حفظ کنید.
- دادهٔ SQLite و PostgreSQL را با importer صریح وارد MongoDB خالی کنید؛ سرور فعال را به URI مربوط به SQL وصل نکنید.
- پیش از بازیابی آفلاین، تمام نویسندگان را متوقف کنید؛ بازیابی آنلاین پنل، HTTP `409` برمی‌گرداند.
- بررسی دیتابیس و آزمون integration مخصوص replica set را روی محیط انتخاب‌شده اجرا کنید.

دستورهای عملیات در [دستورهای دیتابیس](./Database-Commands)، [به‌روزرسانی](./Updating) و [متغیرهای محیطی](./Environment-Variables) هستند. آزمون محلی موفق، نشانهٔ موفقیت استقرار ابری، ورود داده یا بازیابی خاصی نیست.
